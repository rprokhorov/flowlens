# FlowLens — план работ

Инструмент анализа потока задач для тимлида. Kanban. Источник — Jira Data Center,
архитектура source-agnostic (коллекторы подключаемые).

## Принятые решения

| Решение | Значение |
|---|---|
| Стек | Python 3.12 + FastAPI + Postgres 16 + React/TS + ECharts |
| Источник истины | Event log (`ticket_event`), всё производное пересчитываемо |
| Слои | RAW → EFFECTIVE (согласование) → METRICS |
| Время | Считаем календарное И рабочее одновременно, переключатель в UI |
| Календарь | На команду, fallback на глобальный |
| Атрибуция к людям | По времени владения (не по последнему assignee) |
| Единица работы | Task и Sub-task (subtask'и живут на доске), с флагом фильтрации |
| Класс обслуживания | issue_type × priority |
| Обмен коллектор↔ядро | NDJSON по фиксированному контракту |
| Развёртывание | Локально, docker-compose |

## Каноническое отображение статусов

| Jira | Фаза | active_work | queue |
|---|---|---|---|
| new | backlog | нет | да |
| in progress | in_progress | да | нет |
| blocked/hold | blocked | нет | да |
| qa | verify | да | нет |
| release | done_pending | нет | да |
| done | done | — | — |

Блокировка: отдельный статус + ортогональный флаг `is_blocked` на интервале,
запоминается `blocked_from_status_id`.
Cycle time включает release (команда отвечает «от и до»).

## Этап 1 — Фундамент расчётов ✅

**Цель:** из event log получать корректные интервалы и метрики. Проверяется SQL,
без UI и без Jira.

- [x] 1.1 Каркас проекта: poetry/uv, ruff, mypy, pytest, docker-compose с Postgres
- [x] 1.2 Применение DDL через alembic, миграция 001
- [x] 1.3 Модуль рабочего календаря: `business_seconds_between(a, b, calendar)`,
      учёт TZ, праздников, перенесённых суббот, DST
- [x] 1.4 Генератор синтетических данных: тикеты с известными заранее метриками
- [x] 1.5 Построитель `ticket_interval` из `ticket_event` (сворачивание переходов
      статуса и assignee в интервалы, обработка открытых интервалов)
- [x] 1.6 Расчёт `ticket_metrics` поверх интервалов
- [x] 1.7 `person_workload_daily`
- [x] 1.8 Тесты: краевые случаи (переоткрытие, откат назад, нулевые интервалы,
      тикет создан и закрыт в нерабочее время, переход через выходные)

**Готово когда:** на синтетике 200 тикетов метрики совпадают с ожидаемыми до секунды,
пересчёт всей БД идемпотентен.

**Результат (2026-09-01):** 124 теста, 10 эталонных сценариев сходятся до секунды.
Postgres локально через brew (не docker — демон не установлен). На 6000 тикетов
и 46716 событий: загрузка 9 с, полный пересчёт 12 с, идемпотентность подтверждена
сверкой хешей. Календарь покрыт 30 тестами включая DST, праздники и переносы.

## Этап 2 — Коллектор Jira DC ✅

**Цель:** реальные данные за год в БД.

- [x] 2.1 Контракт NDJSON: json-schema для ticket/event/comment/declared_date
- [x] 2.2 Клиент Jira DC: auth, пагинация, rate limit, ретраи
- [x] 2.3 Выгрузка тикетов + changelog + комментарии
- [x] 2.4 Маппинг полей через конфиг (`source_profile`), включая declared-даты
- [x] 2.5 Резолвер людей: `person_alias`, слияние по email
- [x] 2.6 Инкрементальная синхронизация по watermark, идемпотентный upsert
- [x] 2.7 CLI: `flowlens sync`, `flowlens import <file.ndjson>`
- [x] 2.8 Первичная загрузка года истории

**Готово когда:** год данных загружен, повторный запуск не создаёт дублей,
интервалы построены.

**Результат (2026-09-01):** контракт NDJSON с валидацией, клиент Jira DC
(пагинация, ретраи, rate limit), маппер полей, резолвер людей, идемпотентный
импорт. 214 тестов. На 6010 тикетов / 46212 событий: импорт 6.9 с, пересчёт 10.5 с.

⚠️ Живое подключение к Jira не проверялось — доступа нет. Протестированы разбор
ответов API на фикстурах и транспорт на мок-сервере; реальный `flowlens sync`
требует проверки при появлении доступа.

Найден и исправлен дефект: `UNIQUE (ticket_id, source_event_id, field)` не ловил
дубли событий без поля (`created`), так как NULL != NULL. Заменено на уникальный
индекс с COALESCE (миграция 002).

## Этап 3 — Согласование и качество данных ✅

**Цель:** честные метрики поверх грязных дат.

- [x] 3.1 Движок политики согласования, `policy_version`
- [x] 3.2 Заполнение `ticket_timeline_fact`
- [x] 3.3 Детекторы аномалий: declared_missing, declared_contradicts_changelog,
      end_before_start, bulk_move, stale_transition, zero_duration_lifecycle
- [x] 3.4 Отчёт качества данных (сначала CLI, потом экран)
- [x] 3.5 Переопределение политики на команду
- [x] 3.6 Пересчёт метрик после смены политики без похода в Jira

**Готово когда:** видно, какая доля тикетов достоверна; можно переключить политику
и увидеть, как изменились цифры.

**Результат (2026-09-01):** 265 тестов. На синтетике распознаны все заложенные
патологии. Показательный случай — тикет, проведённый по доске одним махом:
changelog утверждает 0 часов работы, согласование восстанавливает 81 час
по заявленным датам.

Смена политики пересчитывает 6010 тикетов за 15 с без обращения к источнику;
слой RAW при этом не меняется — проверено тестом.

Найден и исправлен баг: при дневной точности дата сравнивалась с моментом
создания тикета, из-за чего «начал 2 марта» на задаче, созданной 2 марта
в 11:00, считалось ошибкой. Теперь при дневной точности сравнение идёт
по календарным датам, а результат прижимается к моменту создания.

## Этап 4 — API и дашборд ✅

**Цель:** тимлид видит графики.

- [x] 4.1 FastAPI: срезы (период, команда, человек, класс, тип), переключатель
      календарные/рабочие часы, фильтр по confidence
- [x] 4.2 CFD (накопительная диаграмма потока)
- [x] 4.3 Гистограмма cycle time с P50/P85/P95
- [ ] 4.4 Scatter cycle time во времени с трендом (перенесено: гистограмма
      с перцентилями пока закрывает потребность)
- [x] 4.5 Aging WIP с наложением перцентилей — главный экран для дейли
- [x] 4.6 Arrival vs throughput, накопление очереди
- [x] 4.7 Flow efficiency, разбивка времени по фазам
- [x] 4.8 Разрез по сотруднику (нагрузка, не рейтинг)
- [x] 4.9 Экран качества данных
- [x] 4.10 Аннотации interventions (API готов, наложение на графики — позже)

**Готово когда:** все вопросы из списка целей отвечаются кликами в UI.

**Результат (2026-09-01):** 315 тестов. FastAPI + ECharts, тёмная тема,
валидированная палитра, цвет закреплён за фазой. Дашборд проверен
скриншотами на 6010 задачах.

Найденные и исправленные дефекты:
- `closed_at` не заполнялся — все задачи числились открытыми;
- Postgres отдавал `sum()` как numeric → JSON-строки → график сравнивал
  значения лексикографически (в тестах теперь есть проверка типов);
- CFD выполнялся 2 с через соединение «интервал × день»; переписан
  на накопление дельт — 0.1 с;
- «Готово» в CFD затмевало незавершённую работу — скрыто по умолчанию;
- «Куда уходит время» показывало сумму за год («10030 дней») вместо
  медианы на задачу.

## Этап 6 — Прогнозы L2 ✅

- [x] 6.1 Monte Carlo: «когда закончим N задач» и «сколько сделаем к дате»
- [ ] 6.2 Прогноз по epic с учётом иерархии (нужны реальные данные Jira:
      в синтетике иерархия не наполнена)
- [x] 6.3 Сезонность arrival rate (день недели, неделя месяца)
- [ ] 6.4 Детект аномалий потока по классам (перенесено к L3)
- [x] 6.5 Little's Law: оценка потребности в людях

**Результат (2026-09-01):** 374 теста. Monte Carlo на 10 000 прогонов,
перцентили методом ближайшего ранга. Прогноз строится на историческом темпе,
а не на оценках трудоёмкости.

Найденная ошибка проектирования: прямое применение закона Литтла давало
225 задач/день при реальных 11.6 — WIP включал бэклог, а время цикла
считалось только по завершённым задачам. Заменено на `wip_health`:
сравнение измеренного времени цикла с тем, что следует из объёма работы.
Разрыв в 18 раз — содержательный вывод о застое, а не арифметика.

## Порядок и зависимости

```
1 (фундамент) ──> 2 (коллектор) ──> 3 (качество) ──> 4 (UI) ──> 5 (советы)
                                                        └──────> 6 (прогнозы) ──> 7 (LLM)
```

Этап 3 обязателен до 4: показывать графики по недостоверным данным вреднее,
чем не показывать ничего.
