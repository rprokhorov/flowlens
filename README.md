# FlowLens

Анализ потока задач (Kanban) для тимлида: cycle time, CFD, aging WIP,
flow efficiency, нагрузка по людям, прогнозы.

Источник данных — Jira Data Center; архитектура source-agnostic,
коллекторы подключаемые.

## Состояние

Завершены все семь этапов: фундамент расчётов, коллектор Jira, согласование
данных, API и дашборд, наблюдения по правилам, вероятностные прогнозы,
текстовый разбор. Поверх них добавлен слой канбан-метрик: причины блокировок
с разбором по Парето, зафиксированный SLE, матрица переходов с возвратами,
возраст очереди, классы обслуживания и скрытая очередь внутри активных
статусов.

Живое подключение к Jira и к API Anthropic не проверялось — нет доступа.
Коллектор протестирован на фикстурах и мок-транспорте, остальное работает
на синтетических данных. Подробности в `PLAN.md`.

## Откуда брать данные

| Источник | Как | Что получится |
|---|---|---|
| **Jira** | кнопка «Импорт данных» → «Подключить Jira», либо `flowlens sync --config jira.yml` | всё: changelog, комментарии, заявленные даты |
| **CSV с историей переходов** | кнопка «Импорт данных» или `import-csv` | всё, кроме комментариев |
| **CSV — плоский список** | то же | время цикла и пропускная способность; время по фазам и возвраты — нет |
| **Другой FlowLens** | файл из кнопки «Выгрузить срез» | всё, что было в срезе |

Колонки CSV распознаются по синонимам — русским и английским, разделитель
определяется автоматически. Что не распозналось, показывает
`flowlens import-csv файл.csv --describe`.

Мастер подключения к Jira не требует YAML: он проверяет доступ, читает список
статусов и сам находит `customfield_*` с датами начала и конца работы —
именно на них обычно спотыкается ручная настройка. Найденное показывается
с пометкой «найдено точно» или «похоже — проверьте»: подстановка не того поля
молча испортила бы все метрики. После выгрузки мастер отдаёт готовый YAML
для запуска по расписанию — токен в файл не попадает, остаётся только имя
переменной окружения.

## Подключение к Jira

Настраивается в дашборде: «Импорт данных» → «Подключить Jira». Нужен только
адрес и Personal Access Token — для Data Center логин не требуется, PAT идёт
в заголовке `Authorization: Bearer`. Пара логин/пароль остаётся запасным
вариантом для инсталляций без PAT.

FlowLens проверит доступ, прочитает список статусов и сам найдёт
`customfield_*` с датами начала и конца работы — именно на них обычно
спотыкается ручная настройка. Найденное показывается с пометкой уверенности:
подстановка не того поля молча испортила бы метрики.

Подключение можно сохранить — тогда данные обновляются по расписанию:

```bash
export FLOWLENS_SECRET_KEY=...     # ключ шифрования токенов
export FLOWLENS_SCHEDULER=1        # включить фоновое обновление
```

Токен хранится зашифрованным (Fernet) и наружу не отдаётся никогда — ни в
списке подключений, ни в ответе на сохранение. Смысл не в защите от
администратора базы, а в том, что дамп или бэкап не даёт доступа к Jira.
Без `FLOWLENS_SECRET_KEY` сохранить токен нельзя: молча писать открытый текст
хуже, чем отказаться.

```bash
flowlens sources            # что настроено и когда обновлялось
flowlens sources --sync     # обновить то, чему пора
```

## Несколько команд

Каждая команда считается отдельно: свой календарь, своя классификация статусов,
свои обещания. Это не косметика — `qa` у одной команды означает code review
и активную работу, у другой очередь на ручное тестирование, и от этого
напрямую зависят эффективность потока, время по фазам и WIP.

Настройка — на вкладке «Настройки»: список команд и таблица статусов
с переключателями «работа» / «очередь». Изменение сразу пересчитывает метрики.
Переключатель команды появляется в строке фильтров, когда команд больше одной.

## Архитектура

Три слоя, каждый следующий полностью пересчитывается из предыдущего:

```
RAW        ticket_event + ticket_declared_date   ← источник истины
EFFECTIVE  ticket_interval                        ← свёртка событий в интервалы
METRICS    ticket_metrics, person_workload_daily  ← агрегаты
```

Смена календаря или политики согласования не требует повторного похода
в Jira — достаточно пересчёта.

`ticket_interval` — центральная таблица: отрезок, на котором неизменны
статус и исполнитель. Из неё считаются все графики.

## Быстрый старт

```bash
docker compose up -d          # → http://localhost:8000
```

Поднимает Postgres, накатывает миграции и — если база пуста — заливает
синтетические данные, чтобы дашборд открылся сразу со всеми графиками.
Повторный запуск данные не трогает. Без демо-данных: `FLOWLENS_DEMO=0 docker compose up -d`.

Дальше загрузить свои данные можно кнопкой «Импорт данных» прямо в дашборде —
формат описан там же, в окне импорта.

## Установка вручную

Postgres 16 (локально через brew):

```bash
brew install postgresql@16
brew services start postgresql@16
createdb flowlens
```

Либо через Docker: `docker compose up -d` (порт 5433, поправьте `.env`).

Питон:

```bash
python3 -m venv .venv
.venv/bin/pip install -e .
cp .env.example .env
.venv/bin/alembic upgrade head
```

## Использование

```bash
.venv/bin/flowlens seed-demo --tickets 500 --months 12   # синтетика в базу
.venv/bin/flowlens export-demo --output demo.ndjson      # синтетика в файл
.venv/bin/flowlens import demo.ndjson                    # импорт выгрузки
.venv/bin/flowlens import-csv export.csv --describe      # что распозналось в CSV
.venv/bin/flowlens import-csv export.csv                 # импорт CSV
.venv/bin/flowlens export --output slice.ndjson          # срез для передачи
.venv/bin/flowlens recompute --all                       # пересчёт
.venv/bin/flowlens quality -v                            # качество данных
.venv/bin/flowlens stats                                 # сводка
.venv/bin/flowlens advice                                # что стоит посмотреть
.venv/bin/flowlens forecast                              # вероятностный прогноз
.venv/bin/flowlens sle --fix                             # зафиксировать обещание
.venv/bin/flowlens sle                                   # проверить попадание в него
.venv/bin/flowlens explain                               # текстовый разбор (нужен ключ)
.venv/bin/flowlens serve                                 # дашборд на :8000
```

## Текстовый разбор

`flowlens explain` и кнопка «Получить разбор» на дашборде отдают метрики
модели Claude, которая объясняет их связь. Модель получает уже посчитанные
показатели — она ничего не вычисляет и не может выдумать число, которого
нет во входных данных.

```bash
export ANTHROPIC_API_KEY=...
.venv/bin/flowlens explain --days 90
```

Без ключа команда сообщает об этом и завершается; остальные отчёты
от неё не зависят.

## Дашборд

`flowlens serve` поднимает веб-интерфейс с одиннадцатью вкладками:

| Вкладка | Что показывает |
|---|---|
| Обзор | ключевые показатели, текстовый разбор, наблюдения по правилам |
| Поток | накопительная диаграмма, поступление против закрытия, накопленный разрыв, очередь бэклога |
| Время цикла | распределение с перцентилями, самые долгие задачи |
| Где время | медиана по фазам, работа против ожидания, скрытая очередь, матрица переходов |
| Незавершённое | возраст открытых задач, список висящих |
| Блокировки | вероятность и потери, Парето по причинам, список для стендапа |
| Обещания | действующие SLE, попадание по периодам, классы обслуживания |
| Нагрузка | распределение владения между людьми |
| Прогноз | вероятностные оценки, выборка для прогноза |
| Качество данных | достоверность, обнаруженные проблемы |
| Задачи | таблица с поиском, сортировкой и фильтрами |

Фильтры (период, тип, приоритет, компонент, достоверность) и переключатель
рабочих/календарных часов действуют на все вкладки сразу. Адрес вкладки
попадает в ссылку — можно поделиться конкретным разрезом.

## Просмотр исходных данных

У каждого графика есть кнопка **«Данные»** — она открывает таблицу, из которой
график построен. Числа в разделе качества данных тоже кликабельны и ведут
к списку затронутых задач.

Ключ любой задачи открывает **карточку** с полной историей:

- метрики задачи;
- как ядро определило время работы — история статусов, заявленные вручную даты
  и принятое решение с указанием источника и достоверности;
- путь по доске: длительность каждого интервала, мгновенные переходы отмечены
  отдельно;
- сырой журнал событий, как его отдал источник;
- комментарии и связи.

Это тот уровень, на котором видно расхождение между тем, что записано
в истории статусов, и тем, что было на самом деле.

Интерфейс подхватывает тему системы; кнопка в правом верхнем углу переключает
вручную. ECharts подключён локально — интернет не нужен.

Сбор данных из Jira (нужен `JIRA_TOKEN` в окружении):

```bash
cp examples/collector.jira.yml my-jira.yml   # поправьте под свою инсталляцию
export JIRA_TOKEN=...
.venv/bin/flowlens sync --config my-jira.yml --dry-run --output dump.ndjson
.venv/bin/flowlens sync --config my-jira.yml
```

## Согласование данных

Ключевая проблема реальных данных: сотрудники двигают задачи на доске
с опозданием, а настоящие даты проставляют вручную. Получается два
противоречивых источника истины.

FlowLens хранит **оба** сигнала сырыми и выбирает итоговое значение
по настраиваемой политике, помечая расхождения:

```bash
# посмотреть, что будет, если верить только истории статусов
.venv/bin/flowlens recompute-policy --prefer system_only --version system-only

# вернуться к доверию заявленным датам
.venv/bin/flowlens recompute-policy --prefer declared --version default
```

Смена политики пересчитывает метрики из event log — обращение к Jira не нужно.

Обнаруживаемые проблемы: незаполненные даты, даты раньше создания задачи,
перепутанные местами начало и конец, расхождение с историей статусов сверх
порога, проведение задачи по доске одним махом, нулевая длительность работы.

## Разработка

```bash
make test    # pytest
make lint    # ruff
```

Тесты не требуют базы, кроме `tests/test_pipeline_db.py` — он пропускается,
если Postgres недоступен.

## Модель времени

Все длительности считаются одновременно в календарных и рабочих секундах.
Рабочий календарь задаётся на команду (`calendar.workweek`, праздники,
перенесённые рабочие субботы), учитываются таймзона и переход на летнее время.

## Доска

| Статус | Фаза | Активная работа | Очередь |
|---|---|---|---|
| new | backlog | нет | да |
| in progress | in_progress | да | нет |
| blocked/hold | blocked | нет | да |
| qa | verify | да | нет |
| release | done_pending | нет | да |
| done | done | — | — |

`qa` считается активной работой: фактически это code review, тесты
автоматические. `release` включён в cycle time — команда отвечает «от и до».

Блокировка хранится и как фаза, и как флаг `is_blocked` на интервале,
с запоминанием `blocked_from_status_id` — из какого статуса ушли в блок.
