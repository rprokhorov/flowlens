# FlowLens

Инструмент анализа потока задач для тимлида: где застревает работа, сколько
времени она реально занимает, что мешает и когда всё это закончится.

Целевая система — Jira Data Center, но архитектура source-agnostic:
коллекторы подключаемые, ядро о специфике источника не знает.

## Зачем это построено

Тимлиду нужно отвечать на вопросы: успеем ли к дате, где застревают задачи,
сколько времени уходит на ожидание против работы, кто перегружен, помогло ли
изменение процесса. Готовые дашборды Jira на них не отвечают, а Grafana
не рисует CFD и Monte Carlo.

**Главная проблема данных, ради которой всё спроектировано именно так:**
сотрудники двигают задачи на доске с опозданием, а настоящие даты работы
проставляют вручную задним числом. Получается два противоречивых источника
истины об одном событии. Инструмент обязан это видеть, а не сглаживать.

## Архитектура

Три слоя, каждый следующий полностью пересчитывается из предыдущего:

```
RAW        ticket_event + ticket_declared_date   ← источник истины, неизменен
EFFECTIVE  ticket_timeline_fact + ticket_interval ← решения ядра
METRICS    ticket_metrics + person_workload_daily ← агрегаты
```

Смена календаря или политики согласования пересчитывает слои 2 и 3
без обращения к Jira. Слой RAW при этом не меняется — это проверено тестом.

### ticket_interval — центральная таблица

Отрезок, на котором неизменны статус и исполнитель. Рвётся при смене любого
из них. Из неё считается всё: CFD, WIP, время по фазам, нагрузка людей,
flow efficiency, aging.

Нулевые интервалы **сохраняются**: мгновенный проход через статус — это факт,
признак разгребания доски задним числом, а не мусор.

### Граница коллектор / ядро

Обсуждалась отдельно и решена так: **коллектор нормализует форму данных,
ядро решает, что правда.**

| Коллектор знает | Ядро знает |
|---|---|
| Как ходить в API, пагинация, авторизация | Что такое «начало работы» |
| Что `customfield_10014` — это start date | Как разрешать противоречия сигналов |
| Как называется статус в этой инсталляции | Что такое рабочий календарь |
| Формат changelog | Какие аномалии считать аномалиями |

Коллектор отдаёт **и** changelog, **и** заявленные даты — сырыми, рядом.
Если бы он «чинил» их сам, диагностика пропала бы, а логика дублировалась
в каждом коллекторе.

## Специфика команды пользователя

Доска: `new → in progress → blocked/hold → qa → release → done`

| Статус | Фаза | Активная работа | Очередь |
|---|---|---|---|
| new | backlog | нет | да |
| in progress | in_progress | **да** | нет |
| blocked/hold | blocked | нет | да |
| qa | verify | **да** | нет |
| release | done_pending | нет | да |
| done | done | — | — |

- **`qa` — активная работа**, а не очередь: фактически это code review,
  тестирование автоматическое. Если задачи начнут там подвисать в ожидании
  ревьюера, это проявится бимодальным распределением времени в статусе —
  тогда фазу надо будет разделить.
- **`release` включён в cycle time**: команда отвечает «от и до».
  Отдельно считается `release_wait` — стоимость релизного цикла.
- **Блокировка** — отдельный статус, но в схеме это ещё и ортогональный флаг
  `is_blocked` на интервале с запоминанием `blocked_from_status_id`
  (откуда ушли в блок). Позволяет считать блокировки в контексте фазы.
- **Sub-task живут на доске самостоятельно** (от них пытаются отказаться),
  поэтому считаются единицей работы, но помечены флагом для фильтрации.
- **Класс обслуживания** = issue_type × priority.
- **Даты работы**: дата+время, заполнены примерно у 75% задач,
  глубина истории — год.

## Ключевые решения и почему именно так

**Event log как источник истины** (не снапшоты) — чтобы можно было пересчитать
историю при смене маппинга статусов или календаря.

**Рабочее и календарное время считаются одновременно** и хранятся рядом
(`duration_business_s`, `duration_calendar_s`) — переключатель в UI бесплатный.

**Атрибуция к людям по времени владения**, а не по последнему assignee.
Метрика подаётся как распределение нагрузки, не как рейтинг: владеть задачей
и работать над ней — не одно и то же. Формулировки в UI и в правилах
намеренно говорят о процессе, а не оценивают людей.

**Перцентили методом ближайшего ранга**, без интерполяции: показываем реально
наблюдавшееся значение, а не среднее между двумя задачами.

**Прогноз на историческом темпе**, не на оценках трудоёмкости. Результат —
распределение, а не дата: одна дата всегда скрывает разброс.

**Отчёт о качестве данных — первый экран.** Пока метрикам нельзя доверять,
остальные выводы преждевременны. Правило `data_quality` проверяется первым
в движке наблюдений.

## Слой согласования (самая важная часть)

Для каждой границы работы (`work_start`, `work_end`) хранятся:

- `system_at` — из changelog: точный timestamp, неверная семантика;
- `declared_at` — из поля: верная семантика, дырявые данные;
- `effective_at` — решение политики + `chosen_source` + `confidence`;
- `anomaly_flags` — что не так с этими данными.

Политика настраивается (`prefer: declared | system | system_only`, порог
расхождения, поведение при конфликте) и версионируется. Пересчёт всей базы
под другой политикой — 15 секунд на 6000 задач.

**Показательный случай — DEMO-6:** задачу провели по доске за 30 секунд
в пятницу вечером. Changelog утверждает 0 часов работы, согласование
восстанавливает 81 час по заявленным датам и помечает `bulk_move`.

Детекторы аномалий: `declared_missing`, `declared_before_created`,
`declared_after_now`, `end_before_start`, `declared_contradicts_changelog`,
`declared_only_partial`, `bulk_move`, `zero_duration_lifecycle`,
`no_system_signal`, `completed_without_work`.

## Команды

```bash
flowlens export-demo --output demo.ndjson --tickets 6000 --months 12
flowlens import demo.ndjson        # + автоматический пересчёт
flowlens recompute --all
flowlens recompute-policy --prefer system_only --version test
flowlens quality -v
flowlens advice --days 90
flowlens forecast --weeks 4
flowlens explain --days 90         # нужен ANTHROPIC_API_KEY
flowlens serve --port 8000
flowlens stats

flowlens sync --config my-jira.yml --dry-run --output dump.ndjson
flowlens sync --config my-jira.yml    # инкрементально по watermark
```

Постгрес поднят через brew (`postgresql@16`, порт **5432**), не Docker —
демона на машине нет. `docker-compose.yml` в репозитории оставлен для тех,
у кого Docker есть (там порт 5433).

## Дашборд

Девять вкладок с адресацией через hash (`#cycle`, `#quality` — можно дать
ссылку на разрез). Фильтры общие, загрузка по требованию.

Обзор · Поток · Время цикла · Где время · Незавершённое · Нагрузка ·
Прогноз · Качество данных · Задачи

**Просмотр исходных данных — три уровня:**
1. кнопка «Данные» у каждого графика → таблица, из которой он построен;
2. клик по элементу: столбец гистограммы → задачи диапазона, полоса фазы →
   интервалы, число аномалии → затронутые задачи;
3. карточка задачи по клику на ключ → метрики, разбор согласования дат
   (оба сигнала и выбор ядра), путь по доске с длительностями,
   сырой журнал событий, комментарии, связи.

Палитра валидирована на различимость при дальтонизме; цвет закреплён
за фазой, фильтрация не перекрашивает серии. Тёмная и светлая темы.

## Дефекты, найденные по ходу — могут повториться

**`NULL != NULL` обходит UNIQUE.** События без поля `field` (`created`)
дублировались при каждом импорте, потому что `ON CONFLICT` не срабатывал.
Решение — уникальный индекс с `COALESCE(field, '')` (миграция 002).

**Postgres отдаёт `sum()` как numeric** → JSON-строка → график сравнивает
значения лексикографически и рисует ерунду. Нужен явный `CAST(... AS bigint)`.
В тестах API есть проверка типов, чтобы не вернулось.

**CFD через соединение «интервал × день»** работал 2 секунды на 46k интервалов.
Переписан на накопление дельт (+1 на входе в фазу, −1 на выходе,
оконная сумма) — 0.1 секунды.

**Закон Литтла в лоб врёт.** Прямое применение давало 225 задач/день
при фактических 11.6: WIP включает бэклог, а время цикла измерено только
по завершённым. Заменено на `wip_health` — сравнение измеренного цикла
с тем, что следует из объёма работы. Разрыв в 18 раз — содержательный вывод
о застое, а не арифметика.

**Дневная точность дат.** Сравнение `declared < created_at` для точности
`day` давало ложную аномалию: «начал 2 марта» на задаче, созданной 2 марта
в 11:00. Теперь при дневной точности сравнение идёт по календарным датам,
а результат прижимается к моменту создания.

**Горизонт генератора.** Задавался как 11:00 текущего дня, поэтому вечерние
запуски создавали события в будущем. `move_to` и `assign` вообще не
проверяли горизонт — только `stay()`. Теперь горизонт — фактический момент.

**Генератор синтетики правился пять раз** — он честно воспроизводит
патологии, но сначала отправлял задачи работать в будущее, копил весь WIP
в одной фазе (проверка горизонта стояла после блока `qa`) и оставлял 2%
годовалых задач открытыми. Каждая правка ловилась тестом инварианта
или взглядом на график.

## Инварианты, которые должны держаться

Проверяются тестами; при доработках не ломать:

- интервалы стыкуются без разрывов, только последний может быть открыт;
- `duration_business_s <= duration_calendar_s`, обе неотрицательны;
- нет событий в будущем;
- `lead_time >= cycle_time`;
- `0 <= flow_efficiency <= 1`;
- у каждой задачи есть метрики и два `ticket_timeline_fact`;
- пересчёт идемпотентен (сверяется по md5 агрегата);
- повторный импорт той же выгрузки не создаёт дублей.

- вызов API Anthropic — разбор протестирован на заглушке клиента.

**Перенесено с обоснованием:** scatter cycle time (гистограмма с перцентилями
пока закрывает потребность), прогноз по epic (нужна реальная иерархия Jira),
детект аномалий по классам обслуживания.

## Как работать с проектом

- Тесты не требуют базы, кроме `test_*_db.py` и `test_api.py` — они
  пропускаются, если Postgres недоступен.
- Тестовые фикстуры **пересоздают базу** через `seed_demo`. После прогона
  тестов данные надо перезалить: `flowlens import <файл>.ndjson`.
- `make test`, `make lint` (ruff по src, tests, migrations).
- Проверять изменения UI скриншотами через headless Chrome: он не кликает,
  поэтому логику модальных окон удобнее гонять функциями в Node
  на реальных ответах API.
- Все тексты интерфейса и комментарии — по-русски.
